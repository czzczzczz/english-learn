## 结论

**同类软件存在，但都只覆盖你需求的一半，没有一个同时做"全局取词 → 翻译朗读 → FSRS 生词本 → 语音互转"。**

- 功能最全的是 **Pot**（19,347★，划词+截图OCR+TTS+生词本插件+快捷键），但仓库 **2026-07-04 后已归档**，插件生态 2025-02 起停更 → 只能当架构参考，不能当依赖。
- 学习闭环最完整的是 **启言 QiYan**（FSRS 单词本+查词+划词），但划词只在其内置阅读器（EPUB/PDF）里生效，不是任意软件。
- **语音双向对话**这一块：桌面端开源实现未检索到（零命中），是真正的空白。

定位建议：自研"取词层 + 无焦点弹窗"，其余组件全部复用现成开源件。

## 首选方案：自研 Tauri 2 外壳（MIT）+ 拼装组件

```
取词层 (Rust)    UIA TextPattern 优先 → SendInput Ctrl+C + 剪贴板快照恢复 兜底 → 截图 OCR 终极兜底
弹窗层            always-on-top 无焦点窗口 (WS_EX_NOACTIVATE)，鼠标附近定位，Esc 关闭
语言层            ECDICT 离线查词 + 可插拔翻译（LLM / DeepL / 免费接口）+ TTS 抽象（在线 edge / 离线 sherpa）
记忆层            SQLite 生词表 + FSRS 调度 + 导出 Anki / CSV
语音层            全局热键 → 录音 → VAD 切句 → whisper/sherpa ASR → 翻译 → TTS 回读
```

工作量：单人 **5–7 周** 出可用 MVP。其中取词层占约 1/3 时间，也是唯一真正的技术风险点。

**为什么不直接 fork Pot**：上游归档、Tauri 1.6 老栈、插件体系无人维护；你后续要加语音对话和 FSRS，改动面会超过重写成本。
**为什么不 fork 启言**：它的强项是阅读器 + 复习，弱项正好是你要的全局取词与语音，且 Electron 常驻内存偏高。

## 风险与备选

| 风险 | 影响 | 缓解 |
|---|---|---|
| 剪贴板兜底污染 / 终端·游戏取词失效 | 核心体验 | UIA 优先、备份恢复剪贴板、OCR 兜底；先做命中率实测再定架构 |
| Edge TTS 非官方接口可能失效 | 朗读功能 | TTS 抽象成接口，离线 sherpa-onnx 兜底 |
| 弹窗抢焦点打断用户输入 | 体验 | NOACTIVATE 窗口 + 不激活，验收用"在 VSCode 输入时弹窗"场景 |
| GPL 传染 | 开源协议受限 | 不链接 Pot/Selection 代码，自研取词；ECDICT(MIT) 可用 |
| 语音链路延迟/噪音 | 可用性 | 本地流式 ASR + 按住说话 + VAD 断句 |

**放弃条件**：如果最终只想服务网页阅读，就别做桌面端——浏览器扩展 + Anki 已经够，成本差一个量级。
